# КОД — Кабінет організаційних документів

Система електронного документообігу для організації **будь-якої сфери** — компанії, державної установи, навчального чи медичного закладу, громадської організації: документи з маршрутами погодження та **кваліфікованим електронним підписом у браузері**, кілька організацій з довільною структурою (департаменти, управління, відділи, сектори, філії), ролі й дозволи за посадами, новини, профіль користувача та адмін-панель.

> Система не прив'язана до доменної сфери: організації, їхні підрозділи, назви рівнів структури (типи підрозділів) і ролі адміністратор налаштовує сам, без змін у коді.

## Можливості

| Модуль | Що вміє |
| --- | --- |
| **Документи** | Реєстр із вкладками («Очікують мого підпису», «Створені мною», «Я в маршруті», «Підписані мною», «Усі доступні»), пошук, фільтри, сортування, пагінація. Створення документа: файл до 25 МБ, вид (наказ, розпорядження, службова записка, договір, акт, положення, заява…), підрозділ, маршрут **послідовний** або **паралельний**. Статуси: чернетка → на підписанні → підписано / відхилено → архів. Автор **редагує** чернетку або відхилений документ (файл, реквізити, маршрут); під час повторного надсилання підписи на незміненому файлі зберігаються, а заміна файлу анулює всі підписи. Автоматичні реєстраційні номери `РРРР/NNNNNN`. |
| **Електронний підпис** | Підпис документів і будь-яких файлів **тільки на фронтенді** — офіційною бібліотекою ІІТ EUSignCP-JS 1.3.74 у Web Worker. Ключ і пароль ніколи не залишають браузер. Формати **CAdES** (зовнішній і внутрішній), **XAdES**, **PAdES**, **ASiC-S**, **ASiC-E**. Рівні **B-B / B-T / B-LT / B-LTA**. Окрема сторінка перевірки підпису (підписувач, сертифікат, час підпису або позначка часу). Підписання довільних файлів записується в журнал аудиту — лише назви файлів, формат і сертифікат, без вмісту. |
| **Новини** | Стрічка карток із категоріями й пошуком, закріплені новини, обкладинки, Markdown без сирого HTML (захист від XSS), чернетки та публікація. |
| **Структура** | Кілька **організацій** в одному кабінеті (групи компаній, установа з дочірніми підприємствами, незалежні організації), у кожної — дерево підрозділів довільної глибини. **Каталог типів підрозділів** («Організація», «Департамент», «Відділ», «Сектор», «Філія»… або власні — «Кафедра», «Цех», «Відділення») з іконками. Сторінка підрозділу з організацією, до якої він належить, і працівниками (керівники — першими). |
| **Профіль** | Особисті дані, посади, доступні модулі та дозволи. **Мова інтерфейсу** (українська / English). Зміна пароля, резервні коди 2FA, **перелік активних сесій із завершенням**. |
| **Адміністрування** | Користувачі: створення з тимчасовим паролем, кілька посад, індивідуальні надання й заборони дозволів, блокування, скидання пароля, скидання 2FA, завершення сесій. **Імпорт** (XLSX/CSV, перевірка без збереження, транзакційне застосування, файл з тимчасовими паролями) та **експорт**. Ролі з матрицею дозволів, керування структурою, журнал аудиту. **Кожна організація адмініструє себе сама**: користувачі, структура й новини — лише в організаціях посад адміністратора, увесь кабінет — лише для адміністратора всіх організацій. |
| **Мови** | Український та англійський інтерфейс: сторінки, повідомлення валідації й помилок, REST API, скрипти підпису та вся довідка. Мова зберігається в профілі й діє на всіх пристроях, до входу — перемикач на сторінці входу. |
| **Довідка** | Інструкція користувача на сторінці `/help` українською та англійською, доступна всім: 11 розділів і 60 тем — вхід і 2FA, документи, підпис, новини, організації та структура, профіль, адміністрування (зокрема в межах організацій), ролі, запитання та відповіді. Покрокові інструкції з точними назвами кнопок, зміст із підсвіткою поточної теми, пошук із виділенням збігів, прямі посилання на теми, друк / PDF. Кожен розділ показує, чи доступний він читачеві, а довідник ролей і дозволів будується з коду. |

Самостійної реєстрації немає: облікові записи створює або імпортує адміністратор (фахівець з персоналу своєї організації).

## Технології

- **.NET 10 / C# 14** (primary constructors, `field`, extension members, collection expressions), рішення у форматі **`.slnx`**, Central Package Management.
- **ASP.NET Core Blazor Web App**: static SSR + enhanced navigation + streaming rendering за замовчуванням; **Interactive Server** для складних форм (створення документа, редактори користувачів, ролей, підрозділів і новин, імпорт).
- **ASP.NET Core Web API** (REST, `/api/v1`), OpenAPI + Scalar UI у Development.
- **ASP.NET Core Identity**: `SignInManager`, `UserManager`, TOTP-автентифікатор, резервні коди, lockout, security stamp.
- **Entity Framework Core 10 + PostgreSQL** (Npgsql, snake_case, `citext` для регістронезалежного пошуку, `xmin` як токен конкурентності).
- ClosedXML і CsvHelper (імпорт та експорт), Markdig (новини), QRCoder (QR-коди 2FA).
- **Serilog**: консоль, файл із щоденною ротацією, таблиця `logs` у PostgreSQL.
- **StyleCop.Analyzers** + .NET analyzers, `TreatWarningsAsErrors`, обов'язкова XML-документація англійською.
- xUnit v3 на Microsoft Testing Platform.

## Архітектура (Clean Architecture)

```
src/
├─ KOD.Domain           Сутності та інваріанти: User, Role, StaffPosition, OrganizationUnit, UnitType,
│                       Document (маршрут, підписи), NewsArticle, AuditEntry, UserSession;
│                       каталог дозволів і типові ролі; каталог перекладів (Localization/Texts).
│                       Без EF Core та вебу.
├─ KOD.Application      Сценарії (DocumentService, OrganizationService, UnitTypeService, UserService…), DTO, Result-патерн,
│                       пагінація, правила доступу (IPermissionResolver, IAccessScope),
│                       абстракції інфраструктури.
├─ KOD.Infrastructure   EF Core/PostgreSQL, міграції, сидінг, Identity (SignInManager з обов'язковою 2FA,
│                       claims factory з дозволами, серверне сховище сесій), файлові сховища,
│                       XLSX/CSV, Markdown, інспектор CMS-підписів, аудит.
└─ KOD.Web              Хост: Blazor-сторінки, REST-контролери, автентифікація/авторизація,
   │                    безпекові middleware, проксі до ЦСК, JS інтеграції підпису (wwwroot).
   └─ DesignSystem      Дизайн-система: компоненти (Button, Card, DataGrid + Pagination, Tabs, Dialog,
                        Timeline, DatePicker, OtpInput, PasswordReveal, ValidationError, скелетони…)
                        і шляхи ресурсів; стилі, скрипти, іконки й шрифт — у wwwroot.
tests/
└─ KOD.UnitTests        Доменні правила, доступ, адміністрування в межах організацій (EF Core InMemory),
                        транслітерація, пагінація, безпечний Markdown, повнота англійських перекладів.
```

Залежності спрямовані всередину: `Web → Infrastructure → Application → Domain`. Дизайн-система — частина `KOD.Web` (простір імен `KOD.Web.DesignSystem`): окремий проєкт лише додавав `_content/…`-шляхи та ще одну збірку, а інших споживачів у неї немає. Компоненти дизайн-системи не залежать від сторінок і сервісів застосунку — за потреби їх легко знову винести в Razor Class Library.

## Організації та структура

- **Тип підрозділу** (`UnitType`) — запис каталогу, який веде адміністратор: назва рівня у словнику організації, код, іконка, порядок і позначка **«Це організація»**. Під час першого запуску створюються типові: «Організація», «Департамент», «Управління», «Відділ», «Сектор», «Служба», «Група / команда», «Філія / представництво»; їх можна перейменувати, видалити (якщо не використовуються) і доповнити.
- **Організація** — підрозділ, тип якого позначено як організацію. Лише організації можуть стояти на верхньому рівні дерева; організацію можна вкласти в іншу (дочірнє підприємство в холдингу). Організація підрозділу — найближча організація вище за деревом.
- Перша організація створюється під час запуску з налаштувань `Seed:Organization*`, решту — в адмін-панелі («Нова організація»).
- Коди підрозділів і типів унікальні для всього кабінету (вони використовуються в імпорті користувачів). Людина може мати посади в кількох організаціях; її обліковим записом керують адміністратори цих організацій (див. «Адміністрування в межах організацій»).
- Новина належить організації або всьому кабінету: редагують її адміністратори новин цієї організації, а читають працівники всіх організацій. Ролі, каталог типів підрозділів і журнал аудиту спільні для всього кабінету.
- Реєстраційні номери документів (`РРРР/NNNNNN`) поки що наскрізні для всього кабінету: так номер однозначно ідентифікує документ між організаціями. Окремі журнали реєстрації для кожної організації (лічильник на організацію й рік із префіксом організації) — можливе розширення `DocumentNumberGenerator`.

## Ролі та дозволи

Доступ надається **посадами**: користувач може обіймати кілька посад у різних підрозділах, кожна посада має **роль** (набір дозволів), а підрозділ посади визначає **область видимості** документів. Ефективні дозволи = дозволи всіх ролей ∪ індивідуальні надання − індивідуальні заборони. Модуль показується, якщо є хоча б один його дозвіл.

Типові ролі спільні для більшості організацій (назви, описи й дозволи редагуються в адмін-панелі, а ролі своєї сфери — «Декан», «Головний лікар», «Керівник проєкту» — створюються як власні): **системний адміністратор** (завжди всі дозволи), керівник організації, заступник керівника, керівник підрозділу, заступник керівника підрозділу, діловод, фахівець з персоналу, фахівець з комунікацій, працівник, зовнішній користувач (контрагент, клієнт, слухач, здобувач — без доступу до структури). Роль може бути позначена як **керівна посада** — її власників показано першими у складі підрозділу.

Видимість документів: автор і учасники маршруту бачать завжди; `documents.view.unit` — документи своїх підрозділів і всіх вкладених; `documents.view.organization` — документи всієї організації своїх посад з усіма її підрозділами; `documents.view.all` — документи всіх організацій кабінету.

Захист від ескалації привілеїв: без `roles.manage` не можна призначити роль, що дає більше прав, ніж має сам адміністратор, і не можна керувати обліковим записом із ширшими правами.

### Адміністрування в межах організацій

Адміністративні дозволи мають **область дії** так само, як перегляд документів (`documents.view.organization` ↔ `documents.view.all`):

| Дозвіл | Діє в межах організацій посад | Увесь кабінет — з `administration.all` |
| --- | --- | --- |
| `users.view`, `users.export` | облікові записи з хоча б однією посадою в цих організаціях; експортуються лише посади в них | усі облікові записи, зокрема без посад |
| `users.manage` | посади — лише в підрозділах цих організацій; особисті дані, e-mail, блокування й індивідуальні дозволи — лише для облікових записів, **усі** посади яких у цих організаціях | усі облікові записи |
| `users.security` | пароль, 2FA, сесії — лише для облікових записів, усі посади яких у цих організаціях | усі облікові записи |
| `users.import` | коди підрозділів лише цих організацій; оновлюються лише облікові записи, усі посади яких у них; новий обліковий запис — обов'язково з посадою | без обмежень |
| `structure.manage` | створення, зміна й переміщення підрозділів і дочірніх організацій усередині цих організацій | також організації верхнього рівня, перетворення організації на звичайний підрозділ, каталог типів підрозділів |
| `news.manage` | новини цих організацій | також новини всього кабінету |

- **Організації посад** — організація кожної посади (найближча вище за деревом, `OrganizationTree.OrganizationOf`) з усіма її підрозділами та вкладеними організаціями. Ураховуються лише посади, **роль яких надає саме цей дозвіл**: фахівець з персоналу організації А, що за сумісництвом працює в організації Б звичайним працівником, керує користувачами лише в А. Індивідуально наданий дозвіл не прив'язаний до посади й діє в організаціях усіх посад.
- `administration.all` («Адміністрування всіх організацій») поширює всі адміністративні дозволи користувача на весь кабінет. Серед типових ролей його має лише системний адміністратор. Він не надає сам по собі жодних дій — лише розширює область тих дозволів, які вже є.
- **Обліковий запис кількох організацій** (посади і в організаціях адміністратора, і поза ними) адміністратор бачить, але змінює лише посади у своїх організаціях; посади в інших організаціях (зокрема основна) зберігаються як є. Обліковий запис без посад не належить жодній організації — його бачить лише адміністратор усіх організацій, тож адміністратор організації не може залишити користувача без посад.
- Правило реалізовано в Application-шарі (`IAccessScope.GetAdministrationScopeAsync` → `AdministrationScope`), тож однаково діє для Blazor-сторінок і REST API. Чужі облікові записи для адміністратора організації «не існують» (404), а дії над спільними обліковими записами й підрозділами інших організацій повертають 403 з поясненням.
- `roles.manage` і `audit.view` залишаються загальнокабінетними: ролі й журнал аудиту спільні для всіх організацій. Надавайте їх лише адміністраторам усього кабінету.

## Безпека

- **Вхід через ASP.NET Core Identity** (`SignInManager.PasswordSignInAsync` → `TwoFactorAuthenticatorSignInAsync`). **2FA обов'язкова**: після пароля користувача без автентифікатора спрямовують на прив'язку (QR + ключ, TOTP RFC 6238), потім видаються 10 резервних кодів. Хто входить із **тимчасовим паролем, спочатку замінює його**, і лише потім прив'язує автентифікатор — тимчасовий пароль перестає діяти до прив'язки 2FA.
- **TOTP без повторного використання**: кожен код приймається один раз (зберігається останній прийнятий крок часу), допуск розсинхронізації годинника — ±30 с.
- **Секрети в БД зашифровано**: ключ автентифікатора й резервні коди шифруються Data Protection з прив'язкою до користувача (шифротекст, скопійований в інший обліковий запис, не розшифрується); старі незашифровані значення шифруються під час запуску. Самі ключі Data Protection зберігаються зашифрованими — сертифікатом (`DataProtection:CertificatePath`, обов'язково в Production поза Windows) або DPAPI на Windows.
- **Сесійна автентифікація на Identity cookie** (`__Host-kod`, `HttpOnly`, `Secure`, `SameSite=Lax`). Квиток зберігається на сервері (`CookieAuthenticationOptions.SessionStore` → PostgreSQL, зашифровано Data Protection), тож сесії видно в профілі й їх можна миттєво завершити. Сесія завершується після 8 год без активності й **не пізніше ніж через 12 год після входу** (OWASP ASVS L2). Під час блокування (зокрема через імпорт), скидання пароля чи 2FA сесії обриваються й змінюється security stamp.
- Права перечитуються щохвилини — і для звичайних сторінок, і для відкритих інтерактивних (Blazor Server), без перезавантаження. Інтерактивна сторінка перестає працювати, щойно її сесію завершено.
- Форма входу відповідає однаково на неіснуючу пошту, неправильний пароль і тимчасове блокування; про заблокований обліковий запис повідомляє лише тому, хто ввів правильний пароль.
- Паролі: від 12 до 128 символів, перевірка за базою витоків **Have I Been Pwned** (k-анонімність: із сервера йдуть лише перші 5 символів SHA-1; якщо сервіс недоступний — перевірка пропускається з записом у лог).
- Lockout після 5 невдалих спроб (зокрема неправильний поточний пароль і коди підтвердження), rate limiting форм входу й профілю, API та проксі. Нові резервні коди — лише з кодом автентифікатора (step-up).
- Імпорт користувачів дотримується тієї ж ієрархії, що й ручне редагування: не можна змінити чи заблокувати обліковий запис із ширшими правами.
- `X-Forwarded-For` / `X-Forwarded-Proto` приймаються лише від довірених проксі (`ReverseProxy:*`, loopback). Згенерований пароль першого адміністратора записується у файл `App_Data/initial-admin-password.txt`, а не в лог.
- CSRF: антифорджері для форм (зокрема виходу) і заголовок `X-CSRF-TOKEN` для змінюючих REST-запитів.
- Строгий **Content-Security-Policy** без inline-скриптів і `eval`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy`, COOP/CORP, HSTS у Production.
- Приватні файли (документи, підписи) лежать **поза `wwwroot`** (`App_Data/storage`), видаються лише через API після перевірки доступу, з контролем SHA-256. Публічні обкладинки — у `wwwroot/uploads`, із перевіркою сигнатур зображень.
- Журнал аудиту: входи, невдалі спроби, зміни прав, імпорт/експорт, усі дії з документами, підписання файлів (назви й сертифікат, без вмісту).

## Електронний підпис

- Бібліотека — офіційна збірка ІІТ **EUSignCP-JS 1.3.74** (базова бібліотека 1.3.1.224), найновіша з опублікованих: віджет підпису ID.GOV.UA (`id.gov.ua/sign-widget/v20260209/js/euscp.worker.ex.js`, 31.08.2026). Файли `euscpt.js`, `euscpm.js`, `euscp.ex.js` у `src/KOD.Web/wwwroot/lib/eusign` — це без змін вирізані з неї розділи за маркерами ІІТ `//./src/ExtLibrary/euscp/*.js`. Використовується збірка `euscp.ex.js`: тільки вона підтримує PAdES, XAdES і ASiC.
- Бібліотека працює в **окремому Web Worker** (`wwwroot/js/signing/eusign.worker.js`) і завантажується ліниво, коли відкривається панель підпису. Ключ і пароль передаються лише у воркер.
- Підписання — покроковий майстер (`kod-wizard.js` дизайн-системи): **1) документ / файли → 2) параметри → 3) ключ і підпис**. Перейти далі можна лише тоді, коли попередній крок завершено (для документа — після звірки SHA-256), а перед самим підписом умови перевіряються ще раз. Ключ зчитується тільки на останньому кроці й звільняється одразу після підпису, при поверненні назад, закритті діалогу або виході зі сторінки.
- Перед підписом браузер звіряє **SHA-256** файлу із зареєстрованим на сервері. Підпис завантажується на `POST /api/v1/documents/{id}/signatures`. Для CAdES сервер додатково дістає з контейнера дані сертифіката підписувача.
- **Усі підписи в одному файлі.** Перший підписант обирає формат і тип підпису; кожен наступний додає свій підпис до останньої підписаної версії: CAdES — у той самий `.p7s` (`CtxAppendSign`), PAdES — інкрементальний підпис того самого PDF, ASiC — у той самий контейнер (`CtxASiCAppendSign`). Тож останній файл підпису містить документ і всі підписи — його показано в картці як «Документ з усіма підписами», а кожна попередня версія лишається доступною. XAdES додавання не підтримує: його підписи незалежні, кожен над тим самим оригіналом.
- Перед додаванням браузер звіряє SHA-256 останньої версії із зареєстрованим, кількість підписів у ній і те, що вона містить саме цей документ (підписаний PDF починається з оригіналу, внутрішній CAdES містить його). Сервер приймає лише файл, що є попередньою версією плюс рівно один новий підпис (кількість підписантів CMS / підписів PDF / ASiC, PDF — байт-у-байт префікс), і бере сертифікат саме нового підписанта CMS. Прибрати підписанта з маршруту — означає почати ланцюжок заново.
- Файл підпису названо за документом: підписаний PDF має назву оригіналу, контейнери додають своє розширення (`договір.pdf.p7s`, `договір.pdf.asics`, `договір.asice`) — `SignedFileName`.
- **Черга підписання** (особливо для паралельного маршруту): відкриваючи вікно підпису, підписант бере чергу на 10 хв (`POST /api/v1/documents/{id}/signing-session` — у відповіді версія, до якої додавати підпис); інші в цей час бачать «Документ зараз підписує …», і вікно перевіряє чергу кожні 5 с. Закриття вікна чи успішний підпис звільняють чергу. Підпис приймається лише поверх найновішої версії (`BaseSignatureId`), а `Document` має токен оптимістичної конкурентності (`xmin`), тож навіть одночасні запити не загублять підпис — запізнілий підписант підписує останню версію ще раз.
- Ключ і пароль передаються лише у Web Worker. На сервер ідуть тільки готовий підпис із даними сертифіката, публічні запити до надавачів через проксі (OCSP, позначка часу — лише хеш, CMP — ідентифікатор ключа для пошуку сертифіката) і, для інструмента підпису файлів, назви файлів у журнал.
- Запити бібліотеки до OCSP, TSP і CMP-серверів надавачів ідуть через `/api/v1/eusign/proxy`: лише для автентифікованих, allowlist хостів і портів, обмеження розміру, таймаути, rate limit. Через проксі проходять тільки публічні протокольні повідомлення.
- Ключі: **файлові** (Key-6.dat з автоматичним завантаженням сертифікатів через CMP, `*.pfx`/`*.p12`, `*.pk8`, `*.jks`, `*.zs2`) від усіх кваліфікованих надавачів із переліку ЦЗО; можна додати сертифікати вручну.
- **Обмеження наданого архіву**: ця версія бібліотеки підтримує **лише файлові ключі**. Захищені носії (Алмаз-1К, Кристал-1 тощо), хмарні ключі та «Дія.Підпис» потребують окремих компонентів (вебагент ІІТ / сервіси надавачів). В інтерфейсі ці варіанти показано неактивними. Повна криптографічна перевірка ДСТУ 4145 на сервері потребує серверної бібліотеки ІІТ; зараз підпис перевіряється в браузері.
- **Лише реальні надавачі**, тестового середовища немає. Перелік надавачів (`CAs.json`, 33 КНЕДП: ДПС, «Дія», ПриватБанк, monobank, Ощадбанк, ПУМБ, EDIN ID та ін.) і CA-сертифікати (`CACertificates.p7b`, 1003 сертифікати) сервер **сам оновлює** з офіційного джерела ІІТ (`iit.com.ua/download/productfiles/`) під час запуску й кожні 12 год: файли перевіряються (JSON, PKCS#7, розміри, мінімальна кількість записів) і замінюють поточні атомарно, інакше лишається попередня версія. Браузер отримує їх з `GET /api/v1/eusign/providers` і `GET /api/v1/eusign/certificates` (ETag, 304). Копія в репозиторії — запасна на випадок, коли мережі немає під час першого запуску.
- Проксі дозволяє сервери всіх надавачів з поточного переліку, тож новий надавач запрацює без зміни налаштувань.
- **Підписання довільних файлів** (`/signing`) повністю відбувається в браузері: файл не потрапляє на сервер, результат користувач завантажує одразу. Після підпису браузер надсилає на `POST /api/v1/signing/journal` лише назви файлів, формат, рівень і дані сертифіката — вони записуються в журнал аудиту (дія `signing.files-signed`).
- **Перевірка** показує час підпису з атрибута `signingTime`, а якщо його немає (PAdES його забороняє) — час кваліфікованої позначки часу підпису; для PDF без позначки — час зі словника підпису (`/M`), позначений як «вказаний у документі».

## Дизайн-система

Монохромна палітра (білий / чорний) у стилі Дії: великі заокруглені поверхні, «пігулкові» кнопки, шрифт Manrope (variable, SIL OFL), іконки Lucide (ISC). Світла й темна теми, перемикач зберігається в браузері.

Компоненти — у `src/KOD.Web/DesignSystem/Components`, шляхи ресурсів — у `DesignTokens`; стилі `css/kod-ds.css`, скрипти `js/kod-ds.js`, `js/kod-pickers.js`, `js/kod-theme.js`, `js/kod-wizard.js`, спрайт `icons/sprite.svg` і шрифти `fonts/` лежать у `src/KOD.Web/wwwroot`.

- **Кнопки** при наведенні заливаються контрастним кольором теми (у світлій — чорним, у темній — білим) колом від точки, де зайшов курсор; на інверсних поверхнях — протилежним кольором. Той самий ефект мають варіанти вибору, пагінація, кнопки календаря й чипи.
- **Випадні списки й дати**: `select.ds-select` відкриває власний список, компонент `DatePicker` — календар; браузерні вікна не показуються. Джерелом значення лишається нативний елемент, тож працюють і статичні форми (`data-autosubmit`), і прив’язки Blazor. Повна клавіатурна навігація, панелі відкриваються над модальними діалогами.
- **Завантаження**: `GridSkeleton`, `CardSkeleton`, `FormSkeleton` показують заготовки форми контенту, поки дані стрімляться; контент проявляється плавно, а перехід між сторінками супроводжує смуга прогресу.
- Поля вводу показують фокус лише рамкою, без обведення й тіні.
- **Коди 2FA** — `OtpInput`: шість комірок (3 + 3) над справжнім полем, тож працюють вставка й автозаповнення `one-time-code`; на вході та прив’язці автентифікатора форма відправляється після шостої цифри.
- **Паролі** — `PasswordReveal`: кнопка «показати / сховати»; після відправлення форми пароль знову прихований.
- Модальні вікна, випадні списки й зміст довідки мають тонкий заокруглений скролбар без стрілок.

## Запуск

Потрібно: **.NET SDK 10.0.300+**, **PostgreSQL 14+** (розширення `citext` створюється міграцією), довірений dev-сертифікат (`dotnet dev-certs https --trust`).

1. Налаштуйте секрети (вони не потрапляють у репозиторій):

   ```bash
   cd src/KOD.Web
   dotnet user-secrets set "ConnectionStrings:Database" "Host=localhost;Port=5432;Database=kod;Username=postgres;Password=..."
   dotnet user-secrets set "Seed:AdminPassword" "<пароль першого адміністратора, від 12 символів>"
   dotnet user-secrets set "Seed:DemoPassword" "<пароль демо-акаунтів, лише для розробки>"
   ```

2. Запустіть застосунок. Міграції та сидінг виконуються автоматично:

   ```bash
   dotnet run --project src/KOD.Web --launch-profile https
   ```

   Відкрийте <https://localhost:7180>. Перший вхід: `admin@kod.local` з паролем `Seed:AdminPassword`. Якщо пароль не задано, він генерується й записується у `src/KOD.Web/App_Data/initial-admin-password.txt` (видаліть файл після входу). Під час першого входу ви замінете пароль і прив'яжете автентифікатор.

3. У Development (`Seed:DemoData=true`) створюється демонстраційна структура: організація з дирекцією, канцелярією, відділом кадрів, фінансовим та ІТ-департаментами (з відділами й сектором), юридичним відділом, відділом комунікацій і Львівською філією, а також друга організація — благодійний фонд із правлінням і відділом проєктів. Ще створюються 14 демо-акаунтів у різних ролях (`director@kod.local`, `deputy@kod.local`, `head.it@kod.local`, `head.dev@kod.local`, `engineer@kod.local`, `clerk@kod.local`, `hr@kod.local`, `press@kod.local`, `lviv@kod.local`, `external@kod.local`, `fund@kod.local`, `hr.fund@kod.local`, `projects.fund@kod.local` тощо) і новини — загальна, двох організацій. Фахівці з персоналу `hr@kod.local` (перша організація) і `hr.fund@kod.local` (фонд) бачать і змінюють лише облікові записи своєї організації.

```bash
dotnet tool restore
dotnet ef migrations add <Name> --project src/KOD.Infrastructure --startup-project src/KOD.Web --output-dir Persistence/Migrations
```

| `ReverseProxy:KnownProxies`, `ReverseProxy:KnownNetworks` | Довірені reverse proxy (IP / CIDR) для `X-Forwarded-*` |
| `Serilog:MinimumLevel` | Рівні логування (загальний і `Override` для просторів імен) |
| `Logs:FilePath`, `Logs:RetainedFiles` | Файл логу (`App_Data/logs/kod-.log`, новий щодня — `kod-20261026.log`) і скільки файлів зберігати (31) |
| `Logs:DatabaseTable`, `Logs:DatabaseRetentionDays` | Таблиця логів у БД (`logs`, створюється автоматично) і скільки днів зберігати записи (90) |

У Production також:
- задайте `DataProtection:CertificatePath` (поза Windows без нього застосунок не запуститься);
- вкажіть адреси reverse proxy в `ReverseProxy:*`;
- зробіть резервне копіювання БД і `Storage:PrivateRoot`.

## Логи

Serilog пише кожну подію в три місця: **консоль**, **файл** `App_Data/logs/kod-YYYYMMDD.log` (ротація раз на добу, зберігається 31 файл) і **таблицю `logs`** у базі застосунку (час, рівень, повідомлення, шаблон, виняток, властивості в `jsonb`; записи старші за 90 днів видаляються). На кожен HTTP-запит — один рядок із методом, шляхом, статусом, тривалістю, IP та користувачем: сторінки й API — Information, статичні файли й з’єднання Blazor — Debug, запити довші за 3 с — Warning, помилки — Error. Помилки запуску потрапляють у консоль ще до побудови хоста.

## Мови інтерфейсу

- Ключ перекладу — **сам український текст**: `@T("Зберегти")` у Razor, `Texts.T("…")` у C#, `kodDs.t("…")` у JS. Формат зі значеннями — `T("Знайдено {0} документів", count)` (без інтерполяції всередині `T`). Слово з різним значенням у різних місцях — `Texts.In("контекст", "…")` (ключ `контекст|…`): «Довідка» в меню — Help, як вид документа — Certificate.
- Переклади — JSON-файли `src/<Проєкт>/Localization/en/*.json` (`{ "Український текст": "English text" }`), вбудовані в збірки й підхоплені автоматично; JS — `wwwroot/js/i18n/en*.js`. Відсутній переклад показує українську.
- Повідомлення валідації (`ErrorMessage`) лишаються українськими константами й перекладаються під час показу компонентом `<ValidationError>`.
- Мова визначається з профілю (claim `kod:lang`), інакше з cookie `__Host-kod.lang` (перемикач на сторінці входу), інакше українська. Інтерактивні сторінки тримають мову свого з’єднання, тож зміна мови перезавантажує сторінку.
- Дані з БД (назви, записи аудиту) не перекладаються; виняток — типові ролі й типи підрозділів у списках.
- Тест `LocalizationTests` падає, якщо якийсь текст у `T(…)`, `In(…)`, `ErrorMessage`, назвах полів `Guard` чи `kodDs.t(…)` не має англійського перекладу.

## Довідка: як доповнювати

- Структура (розділи, теми, якоря, потрібні дозволи) — у `src/KOD.Web/Components/Pages/Help/HelpContents.cs`. Зміст сторінки й заголовки будуються з неї, тож вони не розходяться.
- Текст розділу — у `Components/Pages/Help/Chapters/<Розділ>Chapter.razor`: `<HelpChapterSection Id="…">` і всередині `<HelpTopicSection Id="…">`. Кнопки й поля інтерфейсу позначайте `<span class="help-ui">…</span>`, покрокові дії — `<ol class="help-steps">`.
- Англійська версія кожного розділу — двійник `Chapters/English/<Розділ>Chapter.razor` з тими самими `Id`; назви розділів і тем перекладаються в `Localization/en/help.json`. Змінюючи розділ, оновіть обидві версії.
- Додаючи можливість у кабінет, опишіть її в довідці з дослівними назвами кнопок і повідомлень.

## Конвенції коду

- Порядок членів класів, оформлення та документацію контролює **StyleCop** (`stylecop.json`, `.editorconfig`), а збірка падає на будь-яке попередження.
- XML-документація англійською для **всіх** типів і членів, включно з приватними. Компоненти Razor мають code-behind (`*.razor.cs`) з документацією. JS документується через JSDoc.
- Сучасний C#: file-scoped namespaces, primary constructors, `field`, extension blocks, collection expressions, `_camelCase` для приватних полів, без `this.`.
- Тексти інтерфейсу пишуться українською в `T(…)` з англійським перекладом у `Localization/en`; код і документація англійською.
